# AGENTS.md: Project AI Conductor

## С чего начать

Проект: новый плагин Odoo для проактивного контроля рисков. Перед изменением кода найди свою задачу, критерии и блокеры в [`.private/9_github_issues.md`](.private/9_github_issues.md). Не бери смежные задачи без необходимости и не восстанавливай старую реализацию из истории как основу нового кода.

**Сначала ищи контекст проекта в `.private/`.** Там находятся требования, аналитика и согласованные решения (TO-BE). Каталог локальный, исключён из Git. Если материалов нет в рабочей копии, используй согласованные ссылки из issue или запроси недостающий контекст; не угадывай решения и не добавляй приватные материалы в Git.

## Обязательные правила

- Следуй задаче и согласованной архитектуре. Если нужна неутверждённая версия, библиотека, СУБД, брокер, модель или иной выбор, не закрепляй его сам: укажи блокер или эскалируй решение владельцу проекта.
- Соблюдай Conventional Commits, Clean Code и KISS. Рассматривай DRY с третьего смыслового повтора и не усложняй код ради устранения дублей. В Python указывай типы явно, включая локальные переменные, и явно преобразуй данные на границах. Докстринги описывают контракт и начинаются с краткого действия в повелительном наклонении. Для функций, методов и создаваемых объектов описывай входные данные, результат и приводи короткий пример вызова. Комментарии объясняют только нетривиальные решения.
- Утренняя сводка работает без модели. В контекст и выдачу агента попадают только необходимые данные, разрешённые пользователю. Для чтения проверяй членство в выбранном проекте (кроме руководителей пилота из группы администратора Project) и штатные права Odoo на проект, компанию, запись и поле. Агенту доступны только узкие инструменты чтения. Публикация и изменение проекта требуют явного подтверждения конкретной версии и серверной проверки прав.
- Не передавай агенту секреты, журналы или окружение. Не коммить секреты, приватные материалы и реальные данные проекта. Журналируй основные действия и ошибки без сырых проектных текстов и секретов; пользователю показывай понятное сообщение без внутренних деталей.
- Пиши и запускай модульные тесты. Перед сдачей изменений в коде дополнительно запускай отдельного субагента на независимое ревью без правок: он проверяет итоговые изменения по критериям задачи. Самостоятельно проверяй его замечания, при необходимости исправляй код или уточняй свой вывод по ревью. Фиксируй выполненные проверки и их результаты; непроведённую проверку не выдавай за выполненную. Обновляй `docs/` вместе с реализацией: документируй только фактический код (AS-IS), ответственность классов и взаимодействия между ними.
