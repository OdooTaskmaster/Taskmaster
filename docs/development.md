## Пилотный стенд

Согласованные версии: **Odoo 20.0**, **Python 3.12**. Для подготовки пользователей нужна отдельная тестовая база с установленным приложением **Project**. Сам плагин Project AI Conductor для запуска скрипта не нужен.

Для подготовки окружения с нуля используйте [инструкцию установки Odoo 20 на Windows](odoo_windows_setup.md). При работе по ней запускайте команды `odoo-bin` через `.\.venv312\Scripts\python.exe` вместо `python`, если окружение не активировано.

Для задач `BL-02.01`–`BL-02.05` используйте [справочник данных Odoo для правил риска](odoo_risk_data.md) и [протокол проверки источников на стенде](odoo_risk_data_verification.md).

### Установка каркаса

Разместите каталог плагина в одном из путей `addons_path` тестового `odoo.conf`. В `addons_path` указывается родительский каталог, а в `-i` указывается имя папки самого плагина, не отображаемое название «Project AI Conductor». Например, для папки `project_ai_conductor` из каталога с `odoo-bin` выполните:

```powershell
python odoo-bin -c odoo.conf -d aic_pilot -i project_ai_conductor --stop-after-init
```

Подставьте фактические путь к конфигу, имя тестовой базы и имя папки плагина, если они отличаются. Модель ИИ, брокер и отдельный сервер приложения для загрузки каркаса не нужны. Команда приведена для предстоящей проверки `TECH-01`; на стенде она ещё не выполнялась. Для приёмки зафиксируйте фактическую команду и вывод загрузки.

### Если осталась кнопка Risk analysis

Новый каркас не добавляет эту кнопку. В базе, где был установлен Taskmaster, могут остаться его наследуемые представления: запуск Odoo или установка плагина под новым техническим именем их не отключает.

Для приёмки `TECH-01` установите каркас на отдельной чистой тестовой базе и проверьте, что кнопки нет ни на доске проекта, ни в форме задачи.

Если нужно продолжить работу на прежней **тестовой** базе, войдите под администратором базы и откройте `http://localhost:8069/odoo?debug=1`. Роль `Project / Administrator` у аккаунта `aic-pilot-lead@example.test` не даёт доступа к системному меню **Technical**. Под администратором базы откройте **Settings → Technical → User Interface → Views** и архивируйте только старые наследуемые представления `project.task.kanban.taskmaster` и `project.task.form.taskmaster`.

Если меню недоступно, откройте отдельную сессию Odoo shell с нужной тестовой базой, подставив её имя вместо `aic_pilot`:

```powershell
.\.venv312\Scripts\python.exe odoo-bin shell -c odoo.conf -d aic_pilot --shell-interface python
```

Сначала только выведите имя базы и найденные активные представления:

```python
names = ["project.task.kanban.taskmaster", "project.task.form.taskmaster"]
views = env["ir.ui.view"].search([("name", "in", names), ("model", "=", "project.task"), ("inherit_id", "!=", False), ("active", "=", True)])
print(env.cr.dbname, views.get_external_id(), views.mapped("name"))
```

Если это нужная тестовая база и найдены только ожидаемые представления, выполните `views.write({"active": False})` и `env.cr.commit()`. Если список пуст, ничего не меняйте. После архивации обновите доску и форму задачи. Не меняйте стандартные представления `project` и не удаляйте модуль ради скрытия кнопки: удаление модуля может удалить и связанные записи.

Если кнопка видна и на чистой базе, проверьте имя базы в браузере и `addons_path` фактически запущенного экземпляра Odoo: он может загружать старую копию дополнения.

### Тестовые аккаунты

| Логины (email) | Группа Odoo | Назначение |
|---|---|---|
| `aic-pilot-lead@example.test` | Project / Administrator | Руководитель проектов, без прав системного администратора. |
| `aic-pilot-a1@example.test`, `aic-pilot-a2@example.test`, `aic-pilot-a3@example.test` | Project / User | Участники будущего проекта A. |
| `aic-pilot-b1@example.test`, `aic-pilot-b2@example.test`, `aic-pilot-b3@example.test` | Project / User | Участники будущего проекта B. |

Скрипт [`scripts/pilot_users.py`](../scripts/pilot_users.py) создаёт только аккаунты и назначает группы. Для входа используйте полный логин из таблицы и пароль из конфига. Адреса `example.test` тестовые, почту на них не отправляют. Проекты, задачи, членство в проектах и проверка изоляции команд относятся к отдельной работе. Метки A и B в логинах сами по себе не задают права.

Подготовьте локальный конфиг `scripts/.env.pilot_users.toml` по [шаблону](../scripts/pilot_users.example.toml). Укажите точное имя тестовой базы и заполните семь паролей. Локальный файл исключён из Git, шаблон не содержит паролей. Не передавайте пароли в аргументах команды и не прикладывайте конфиг к PR.

Из каталога исходников Odoo откройте отдельную сессию [Odoo shell](https://www.odoo.com/documentation/20.0/developer/reference/cli.html#shell):

```powershell
python odoo-bin shell -c odoo.conf -d aic_pilot --shell-interface python
```

В открывшейся сессии выполните пример ниже, подставив путь к репозиторию. Для автоматического запуска тот же Python-код можно подать в стандартный ввод отдельного процесса `odoo-bin shell`.

```python
from runpy import run_path
run_path(r"C:/path/to/project-ai-conductor/scripts/pilot_users.py")["run"](
    env, "seed", r"C:/path/to/project-ai-conductor/scripts/.env.pilot_users.toml"
)
```

- `seed` создаёт недостающие аккаунты и восстанавливает ранее архивированные. Если аккаунт уже создан прежней версией скрипта, `seed` обновляет его логин до email-формата и заполняет пустое поле email. Существующий контактный email, пароли, группы и связи не меняются.
- `clean` вместо `seed` архивирует только аккаунты, помеченные скриптом. Они больше не активны, связи с проектами и задачами сохраняются. Для `clean` достаточно корректного `database` в конфиге.
- Если база не совпадает с конфигом или зарезервированный логин занят аккаунтом, который создал не скрипт, операция отклоняется. Успешный запуск фиксирует изменения в базе сам. Используйте свежую сессию без других несохранённых правок.
