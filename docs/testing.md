## Модульные тесты

Запускайте команды из корня репозитория на **Python 3.12**. Для чистого окружения создайте отдельный `.venv` и установите зависимости из [`requirements-test.txt`](../requirements-test.txt). Установка Odoo, доступ к базе, брокер и ключ модели не нужны.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-test.txt
.\.venv\Scripts\python.exe -B -m pytest
```

Если окружение уже активировано, достаточно `python -B -m pytest`. Конфигурация [`pytest.ini`](../pytest.ini) ограничивает автоматический поиск каталогом `tests/`. Для запуска одного файла добавьте его путь, например `python -B -m pytest tests/test_application.py`.

`test_application.py` проверяет импорт прикладного пакета без загрузки Odoo. `test_pilot_users.py` проверяет скрипт тестовых аккаунтов с имитацией ORM. Эти тесты не проверяют загрузку плагина в Odoo, права или вход в реальные аккаунты.

`test_pilot_demo_project.py` проверяет состав демодоски, расчёт относительных дат, защиту базы и режим обновления через имитацию ORM.

## Проверка запуска (TECH-02)

Успешный прогон возвращает код `0`. Чтобы проверить отказ раннера, временно инвертируйте ожидание в `test_application.py`, повторите ту же команду и проверьте `$LASTEXITCODE` в PowerShell: при падении теста он должен быть `1`. Затем восстановите тест и запустите команду снова. Намеренно сломанное ожидание в PR не включайте.

На Windows в чистом окружении с Python 3.12.10 и pytest 8.4.2 команда собрала и успешно выполнила 6 тестов. С намеренно неверным ожиданием результат составил `1 failed, 5 passed`, код выхода `1`. После восстановления ожидания все 6 тестов снова прошли.

## Проверка RR-01 (BL-02.02)

```powershell
python -B -m pytest tests/test_deadline_risk.py
```

Тесты проверяют точный срок до, в момент и после дедлайна, срок без времени до и после местной полуночи, расчёт по календарным датам проекта и исходы для закрытых, архивных и неполных карточек. Основные примеры используют `25.11.2026 09:00` по Москве. Проверка карточки «Исправить поиск по базе знаний» использует данные из демонабора PRJ-03: при сроке два дня назад получаем `RR-01` с отклонением 2 дня. Для этих тестов не нужны база Odoo или доступ к доске.

На Python 3.12.10 с pytest 8.4.2 полный прогон `python -B -m pytest` прошёл: 34 теста, из них 22 для `RR-01`. На стенде ту же карточку прочитали через Odoo shell с правами участника демопроекта и передали её данные в правило. Результат: `RR-01`, 2 календарных дня просрочки. Проверка выполнена в транзакции только для чтения и не проверяет вывод сигнала в интерфейсе Odoo.

## Проверка RR-02 и RR-03

```powershell
python -B -m pytest tests/test_stalled_deadline_risk.py tests/test_assignee_risk.py
```

| Правило | Контрольный вход | Ожидаемый исход |
|---|---|---|
| `RR-02` | Срок через 3 дня, движение 2 календарных дня назад, история полная | Сигнал: 3 дня до срока, 2 дня без движения |
| `RR-02` | Срок сегодня ещё действует; движения нет 2 дня | Сигнал: 0 дней до срока |
| `RR-02` | Движение вчера; срок истёк или до него больше 3 дней (отдельные случаи) | Нет сигнала |
| `RR-02` | В окне, история неполна, недавних переходов не подтверждено | Не оценено |
| `RR-02` | В окне, переходов нет по полной истории, задача создана 2 дня назад | Сигнал с отсчётом от создания |
| `RR-03` | Открыта, список исполнителей подтверждённо пуст | Сигнал, дедлайн не требуется |
| `RR-03` | Один или несколько известных исполнителей либо задача закрыта | Нет сигнала |
| `RR-03` | Открыта, назначения недоступны | Не оценено |

Тесты используют фиксированный календарь и нормализованные входы без ORM. Комментарии не передаются в `RR-02`: в качестве движения учитываются только подтверждённые переходы. Подтверждённое отсутствие значения и недоступные данные проверяются отдельно.

Полный прогон `python -B -m pytest`: **137 тестов прошли** на Python 3.13, в том числе 23 для `RR-02` и 9 для `RR-03`. На стенде через Odoo shell в режиме только чтения карточка «Назначить ответственного за ревизию статей» дала `RR-03`. Для карточки «Настроить ответ при отсутствии инструкции» с близким сроком передали историю как неподтверждённую и получили `RR-02: не оценено`. Срабатывание `RR-02` проверено модульными тестами с полной историей; проверка стенда не подтверждает полноту истории переходов.

## Проверка демодоски PRJ-03

Запустите [подготовку демодоски](development.md#демодоска-prj-03), подтвердите в Odoo количество карточек (19 открытых и 5 закрытых), пять колонок и трёх участников проекта. Для визуального подсчёта снимите стандартный фильтр **Open** и разверните колонку «Готово». Значения ниже относятся к дню **первоначального создания**, до ручных изменений. Это ожидаемые сигналы при проверке правил, а не вывод скрипта.

| Карточка | Контрольные данные | Ожидание |
|---|---|---|
| Исправить поиск по базе знаний | Открыта, создана сегодня, срок 2 дня назад | `RR-01`, несмотря на то что карточка новая |
| Настроить ответ при отсутствии инструкции | Срок через 2 дня, создана 4 дня назад, переходов нет | `RR-02`, если покрытие истории подтверждено |
| Проверить тон ответов по спорным обращениям | Срок через 3 дня, создана 2 дня назад, переходов нет | Граничный случай `RR-02`, если покрытие истории подтверждено |
| Назначить ответственного за ревизию статей | Нет ни срока, ни назначений | `RR-03`; отсутствие срока не равно просрочке |
| Маскировать контактные данные в примерах | Срок через 18 дней, создана 7 дней назад, событий нет | Граничный случай `RR-04`, если покрытие истории подтверждено |
| Убрать дубли при передаче оператору | Срок 5 дней назад, создана 9 дней назад, событий нет | `RR-01` и, при подтверждённой истории, `RR-04`. Если история недоступна, `RR-01` остаётся, `RR-04` не оценено |
| Описать поведение при отключении модели | Срок через 8 дней, создана 6 дней назад | `RR-04` не срабатывает при подтверждённой истории |
| Сверстать форму вопроса | Срок завтра, создана сегодня, есть исполнитель | Нет риска, если источники истории доступны и полны |
| Составить памятку оператору | Есть исполнитель, нет срока, создана сегодня | Нет риска, если история полна; число дней до срока не вычисляется |
| Согласовать границы первой версии / Оценить отдельный канал в мессенджере | Сроки прошли; статусы Done и Cancelled | Исключены из проверки, даже если отображаются на Kanban |

Для вариантов `RR-02` и `RR-04` скрипт задаёт синтетический возраст только новых карточек: в штатном ORM нельзя передать `create_date` при создании. Скрипт не фабрикует записи переходов или комментарии. Если установлено приложение трудозатрат, оно отключено для новой доски. Недоступную ролью историю проверяйте отдельно; пустой chatter или отключённый `mail_tracking` не подтверждают полноту. Обновление дедлайнов не возвращает граничные случаи по возрасту к первому дню.

## AG-01: стенд сравнения моделей

Стенд `tools/model_eval/` проверяется без сети, без Odoo и без ключа модели:

```powershell
python tools/model_eval/run_eval.py --self-test
python -m unittest discover -s tools/model_eval/tests -v
```

Проверено 26.11.2026: self-test проходит, 24 модульных теста проходят. Реальный
прогон моделей требует `ROUTERAI_API_KEY` в `.env` и запускается отдельными
стадиями `probe`, `smoke`, `full`; см. [`tools/model_eval/README.md`](../tools/model_eval/README.md).
Результаты сравнения 15 моделей — в [`tools/model_eval/REPORT.md`](../tools/model_eval/REPORT.md),
принятое решение — в [`tools/model_eval/DECISION.md`](../tools/model_eval/DECISION.md).

## AG-02 и BL-01.05: адаптер модели и журнал

Проверка без сети и без ключа модели, на двойнике транспорта и синтетическом секрете:

```powershell
python -B -m pytest tests/test_model_adapter.py tests/test_audit_log.py
```

Проверено на Python 3.13: тесты покрывают успешный ответ, тайм-аут, ошибку провайдера, неверный формат ответа, отсутствие ключа, endpoint и модели и конфигурацию произвольного OpenAI-совместимого endpoint. HTTP-клиент проверяется на подменённой сессии; не-JSON и не-объект в успешном ответе дают `invalid_response` на границе порта. Проверяются отсутствие сырых ошибок провайдера в обычном traceback и сообщении клиента, отказ строковых значений в метаданных журнала, корреляция событий по UUID и безопасное пользовательское сообщение. Происхождение UUID и числовых данных остаётся обязанностью вызывающего кода. Реальный внешний вызов и интеграция с Odoo не проверяются.
