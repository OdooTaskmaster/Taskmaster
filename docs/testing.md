### BL-01.03 — подтверждение конкретной версии

После исправлений ревью на Python 3.12: полный набор — **635 passed**
(547 существующих + 88 тестов барьера); Ruff новых Python-файлов проходит.

`tests/test_confirmed_action.py` проверяет прикладные порты на двойниках, без
Odoo и реальной записи. Оракул — точные аргументы и число вызовов writer:

| Случай | Вызовы записи за один запрос |
|---|---:|
| Точный текущий снимок, явное подтверждение этим пользователем, текущие права | 1 |
| Нет подтверждения, отмена или отклонение | 0 |
| Другая версия, ID, проект, задача, получатель, действие или текст | 0 |
| Подтверждение другого пользователя / действие вне server allow-list | 0 |
| Отказ прав, `None`, truthy не-bool вместо `True` | 0 |
| Изменение, отмена, исчезновение записи за время проверки прав | 0 |
| Исключение источника или проверки прав | 0 |
| Исключение writer | 1 попытка, без автоматического повтора |

Также проверяются положительные int без bool, непустые строки, запрет подмены
серверной области/подтверждения аргументами, неизменность payload, безопасный
аудит без исходного исключения и текста проекта. Отдельный тест фиксирует
границу #31: два разрешённых запроса пока вызывают writer дважды.
После ревью DeepSeek V4 Flash добавлены прямые проверки конструкторов и
подклассов, версии 1, некорректного второго снимка, сохранения форматирующих
Unicode-символов. Для всех трёх исходов проверены состав безопасного аудита и
сбой настоящего logging handler: исход не меняется, дополнительной записи нет.
Штатный отказ в аудите — `failed` без категории, исключение — `failed` с
`unexpected`; потеря события при сбое журнала допускается явно.

```powershell
python -B -m pytest tests/test_confirmed_action.py -q
python -B -m pytest -q
```

Права ролей и отзыв доступа моделируются `ChangeAccess`, не реальными ACL.
На Odoo, в браузере и при конкурирующих транзакциях эта реализация не проверена:
боевые адаптеры не входят в #23. Запись комментария, хранение подтверждений,
идемпотентность и атомарная защита от конкурентного изменения не реализованы.

### AG-06/AG-07 — комментарии и трудозатраты

27.11.2026, CPython **3.12.12**: полный `python -B -m pytest -q` — **456 passed**
(347 существующих + 109 тестов AG-06/AG-07). Файлы `tests/test_task_activity.py` и
`tests/test_task_activity_verification_guard.py` проверяют параметры до чтения,
пределы 1/20 и 1000/1001, усечение текста, DST-период, отсутствие источника,
ошибки/закрытые поля (включая `project.project`, `res.company`, `uom.uom`),
архивную единицу, ленивый default unit для пустой выборки, повторную проверку
области, отсутствие `sudo`, точные десятичные суммы/корректировки, разделение
единиц, агрегацию по дням, уникальность источников и пустые фрагменты, а также
защиту верификатора от реальной базы. Для 1000 строк одного дня/единицы проверяется
один агрегат и размер компактной JSON-проекции менее 40000 байт (не универсальный
предел и не production-сериализатор). Это ORM-моки, не доказательство реальных
прав. Ruff по изменённым Python-файлам проходит; результаты eval перечислены в PR.

Отдельно создана **новая пустая** база `taskmaster_activity_probe_20261127`
(не копия реальных данных), установлены `project,mail_tracking,taskmaster,hr_timesheet`
с `--without-demo=all` на Odoo 20 ревизии `854619dae`, Python 3.12.12.
[`scripts/verify_task_activity.py`](../scripts/verify_task_activity.py) проверяет
production-читателей с настоящими ACL обычного участника: **37 проверок прошли**.

- Доступная карточка не даёт скрытый комментарий: отдельное ограничение
  `ir.access` отсекает его. Другие задача/период также исключены.
- Тексты 2001 → 2000 символов; отбор 20 фрагментов; каждый с точной ссылкой.
- Входящие и исходящие email включены, системное уведомление исключено.
- Записи 2 + 1,5 дают ровно **3,5** в фактической единице строки; они же
  агрегируются в один `WorklogEntry` за день (count=2, обе ссылки). Запись
  другого сотрудника на 7 недоступна по штатным ACL и не входит в итог/основания.
  Другие дата и задача также исключены. Проверка скрытой записи выполнена
  отдельным обычным ORM-поиском, а не только сравнением итога.
- 1001 доступная запись даёт один агрегированный `WorklogEntry` (count=1000)
  и явно частичную сумму 1000,5: берутся последние строки по дате/ID,
  поэтому исходная запись на 2 вытесняется.
- Очищенная единица компании не блокирует доступные строки; при пустой выборке
  без этой настройки возвращается `unavailable`, не ложный ноль.
- Закрытые `mail.message.body` и `account.analytic.line.unit_amount` дают
  `unavailable`; выключенный учёт — не ноль. Пустая видимая выборка не полная.
- Посторонний пользователь, отсутствующая задача и повышенное окружение
  отклоняются; отзыв членства блокирует следующие вызовы в этой транзакции.
- Все синтетические пользователи, сотрудники, сообщения, записи и ограничение
  доступа откатываются `finally: env.cr.rollback()`; база и установленные модули
  сохранены как отдельный стенд. Исходные базы не обновлялись.

Воспроизведение: **только в новой пустой одноразовой базе**, которую перед
установкой модулей явно пометили SQL-комментарием
`COMMENT ON DATABASE <имя> IS 'taskmaster-disposable-activity-verifier-v1'`.
Имя должно начинаться с `taskmaster_activity_probe_`. Никогда не ставьте этот
маркер на рабочую базу или копию реальных данных. Проверяющий скрипт требует
маркер, точное имя, две переменные подтверждения, admin shell без `dbfilter`.
Маркер — защита от ошибочного выбора, не доказательство пустоты базы.
Не запускайте shell с незавершённой пользовательской работой: rollback общий.

Из внешнего корня Odoo (конфиг и зависимости настроены оператором):

```powershell
$db = 'taskmaster_activity_probe_YYYYMMDD'
python -B odoo-bin -c odoo.conf -d $db -i project,mail_tracking,taskmaster,hr_timesheet --without-demo=all --no-http --stop-after-init
$env:TASKMASTER_VERIFY_DB = $db
$env:TASKMASTER_VERIFY_CONFIRM = 'DISPOSABLE_ROLLBACK_ONLY'
$script = Get-Content custom_addons/taskmaster/scripts/verify_task_activity.py -Raw
$script + "`nrun(env, expected_database='$db')" | python -B odoo-bin shell -c odoo.conf -d $db --no-http --shell-interface python --log-level=error
```

Не проверены здесь: HTTP/RPC-регистрация инструментов, браузерный переход по
новым источникам, конкурентный финальный барьер и нагрузочное время ответа.
Смешанные и архивные единицы, отсутствующий модуль и DST проверены модульно, не на реальном
стенде. Независимое ревью остаётся условием завершения issues.

Запускайте команды из корня репозитория на **Python 3.12**. Для чистого окружения создайте отдельный `.venv` и установите зависимости из [`requirements-test.txt`](../requirements-test.txt). Установка Odoo, доступ к базе, брокер и ключ модели не нужны.

## Проверка чтения задач (BL-01.02)

```powershell
python -B -m pytest tests/test_odoo_task_reader.py
```

В полном прогоне `python -B -m pytest` прошли 96 тестов: 18 для `RR-04`, 12 для адаптера чтения и 66 прежних. Тесты адаптера проверяют членство в выбранном проекте, исключение из этого условия для руководителя, ограничения ORM, минимальный набор полей и отказ при повышенных правах. Для недоступной и отсутствующей карточек результат одинаков. Отзыв членства проверен модульно, без изменения прав на стенде.

На стенде в транзакции только для чтения запустили адаптер с настоящими ролями и членством, без подставного списка карточек. Доступ к интерфейсу Odoo сам по себе не даёт доступ через адаптер.

| Сценарий | Фактический результат |
|---|---|
| Участник демопроекта запрашивает карточки из двух проектов, выбрав свой | Возвращена только карточка выбранного проекта и только разрешённые запрошенные поля |
| Обычный пользователь не входит в проект, но видит его по штатным правилам Odoo | Адаптер не возвращает данные |
| Обычный пользователь не входит в закрытый демопроект | Адаптер не возвращает данные |
| Руководитель пилота не входит ни в один из двух контрольных проектов | В каждом выбранном проекте возвращена доступная по Odoo карточка |

### Python 3.12 и причина недоступности истории — 27.11.2026

Для кода `19bdf52` подготовлено отдельное временное окружение CPython **3.12.12**
(Windows x64, сборка python-build-standalone, установленная через `uv`).

из корневого `requirements.txt` Odoo и `requirements-test.txt` плагина;
версии зависимостей не подменялись ради запуска.

Результаты именно в этом окружении:

- `python -B tools/model_eval/run_eval.py --self-test`: **OK**.
- `python -B -m unittest discover -s tools/model_eval/tests -q`: **24 tests, OK**.

Дополнительно проверены настройки tracking у `stage_id` и `state`, отсутствие
модели `mail.tracking.value` и поля `mail.message.tracking_value_ids`, наличие

финализация tracking вызвана без commit. После перехода инструмент истории

источник и не разбирается как доказательство перехода.

Все изменения откатились. Повторный запрос после rollback подтвердил
6 исходных задач, 0 временных пользователей и 0 маркеров демодоски.

не менялись. Логи содержат только названия проверок, не тексты задач.

**Причина блокера AG-05:** базовый `mail` сохраняет изменения в HTML;
опциональный `mail_tracking` сохраняет также структурированные значения,
но его штатный ACL разрешает их только `base.group_system`. Это проверено
по исходникам установленной ревизии, не установкой модуля на базу.
Установка `mail_tracking` сама по себе не даст доступ обычному участнику.
Отчёт длительности этапов использует агрегаты `duration_tracking`, а не
датированную последовательность переходов, и не заменяет нужный источник.

Для завершения положительной приёмки #35 нужен отдельно согласованный
узкий источник переходов с доступом по задаче/проекту/компании/полям.
Варианты — отдельная ограниченная проекция структурированного tracking
или собственная запись будущих переходов; это **предложение, не реализация
и не утверждённое решение**. Общий ACL на весь технический журнал,
системные права участнику и `sudo` в инструменте не предлагаются.
Включение/восстановление исторического tracking явно вне объёма AG-05.
До согласования источника и положительного ORM-теста истории #35 не завершена.
Отдельные ограничения компаний/полей, открытие ссылки в браузере и повторное
независимое ревью также не подтверждены этим прогоном.

### Эксперимент: штатный tracking и узкая серверная проекция — 27.11.2026

Пользователь разрешил **проверить вариант**, использующий `mail_tracking`
и ограниченный серверный метод. Это не автоматическое утверждение готовности
метода к эксплуатации. Создана отдельная база `taskmaster_history_probe_20261127`
без копирования исходных проектных данных. На Odoo 20.0 `854619dae` / Python
3.12.12 установлены Project, Taskmaster и стандартный Discuss Tracking.
Исходная база `odoo_test` не обновлялась.

Временный прототип (не код рабочего адаптера, не RPC-метод) выполняет:

1. Проверку периода и серверных идентификаторов.
2. Повторную проверку проекта, членства, компании и задачи текущим
   пользовательским окружением через существующий путь чтения; повышенное
   окружение вызывающего отклоняется.
3. Проверку доступности полей `stage_id` / `state` и чтение ID/дат разрешённых
   сообщений выбранной задачи и периода **без повышения прав**.
4. Единственное привилегированное чтение: значения `mail.tracking.value`
   только для уже разрешённых ID сообщений, модели `project.task` и
   разрешённых полей из фиксированной пары `stage_id` / `state`.
   Возвращаемые поля и лимиты заданы сервером, а не входом модели.
5. Проверку видимости обоих этапов обычным окружением и выдачу только
   даты, вида перехода, старого/нового значения и ссылки на сообщение.
   `complete=False`: даже работающий tracking не доказывает непрерывный охват.

**26 проверок прототипа прошли** отдельным сценарием через реальный ORM:

- Подтверждены установленная модель, отсутствие системной группы у участника
  и отказ прямого чтения технического журнала.
- Настоящие ORM-записи смены этапа/статуса создали штатные tracking-значения;
  выполнена финализация tracking без commit. Серверный прототип вернул ровно
  два перехода с точными ID этапов, сохранёнными значениями статуса, датами
  и источниками. Изменение дедлайна и событие другой задачи не попали в выдачу.
- Проверены неполнота непустой/пустой выборки, обратный/слишком широкий период,
  исключение события вне периода, одинаковый ответ для отсутствующей и
  скрытой задачи, отказ повышенному окружению и постороннему участнику.
- Временные реальные ограничения `ir.access` на сообщение и этап отфильтровали
  их до выдачи. Задача другого проекта и задача недоступной компании при
  явном членстве не прочитаны. Отзыв членства учтён при следующем вызове.
- Две проверки групп полей выполнены временной настройкой `Field.groups`
  в процессе shell с очисткой memo доступа и восстановлением в `finally`:

- Участник после вызовов остался без системных прав; общий ACL tracking
  не расширялся.

Синтетические пользователи, проекты, компания, переходы и ограничения
откатились. Отдельный запрос после rollback подтвердил по 0 временных

привилегированного чтения и согласованное развёртывание `mail_tracking`.
Эксперимент не проверял HTTP/RPC-публикацию, конкурирующий отзыв прав,

## Проверка хранилища TECH-03

[`scripts/probe_tech03.py`](../scripts/probe_tech03.py) запускается из корня репозитория на Python 3.12. По умолчанию он проверяет SQLite во временном каталоге. Для сравнения и проверки восстановления запустите второй вариант с Python, в котором доступен `psycopg2` (например, окружение Odoo). Параметр `--pg-port` указывает порт отдельного локального PostgreSQL с тестовой базой `tech03_probe` и ролью `tech03_probe`, которой разрешено создавать схемы в этой базе. | PostgreSQL | 600 из 600 | 0 | 5,93–6,06 | 6,64–6,95 | 17,57 |

Для обоих вариантов сверено число строк каждого процесса; для SQLite дополнительно прошёл `integrity_check`. WAL не запускали: версия SQLite стенда затронута [ошибкой WAL-reset](https://www.sqlite.org/wal.html#the_wal_reset_bug).

Проверка восстановления использовала синтетические сообщение и отметку о публикации в PostgreSQL, а статус в SQLite. При откате согласованной транзакции осталось 0 сообщений и 0 отметок. Проверка не вызывала `message_post`, не отключала реальную БД или процесс и не меняла данные Odoo. Она подтверждает поведение описанной границы на тестовых таблицах, а не готовность интеграции.

**Итог решения.** Владелец проекта утвердил SQLite для сводок, диалогов, версий черновиков и статусов операций. Odoo остаётся источником проектных данных и опубликованных сообщений. Ключ повтора и отметка о применении с ID сообщения должны сохраняться в таблице плагина в одной транзакции с публикацией в Odoo. Тогда сбой записи в SQLite не приводит к повторной публикации. Рабочий адаптер хранения и публикация в рамках TECH-03 не реализуются.

Из корня репозитория в окружении Python 3.12 с установленным `requirements-test.txt`:

Используются изолированные временные SQLite-файлы, не файл рабочего плагина и не база Odoo. Проверка не требует ключа модели, брокера или HTTP-сервера.

| Сценарий | Что проверяется |
|---|---|
| Приём операции, повторный приём и повторное открытие файла | Сохраняются область, состояние и исходные временные метки |
| Завершение с успехом или ошибкой | Повторы не меняют результат; запоздалые обновления не возвращают операцию в очередь |
| Два конкурирующих результата; захват `running` двумя отдельными процессами | Сохраняется один результат, захватывает один исполнитель; второму возвращается конфликт |
| Закрытая другим соединением запись | Ожидание ограничено, ошибка безопасная, незавершённая запись отсутствует |
| Сохранение и повторное открытие сводки | Восстанавливаются время расчёта, ссылки, все четыре типа оснований, точность дат и отсутствующие поля |
| Повторное и конкурентное сохранение одного запуска | Один результат с тем же ID; конфликтующий снимок не заменяет исходный |
| Другой проект, другой получатель или отсутствующий ID | Одинаковый результат: нет данных |
| Отзыв доступа к проекту, задаче, полю, исполнителю или источнику основания | Доверенный тестовый проверяющий отклоняет весь результат; ни закрытая строка, ни её вклад не возвращаются |
| Пустая сводка, неполный результат и сбой | Каждый исход требует текущей авторизации |
| Повреждённый JSON, семантически неверные метрики/покрытие, наивная дата, SQLite-файл или недоступный каталог | Фиксированная ошибка без содержимого и пути |
| Неожиданная ошибка источника прав или всегда истинный объект вместо `bool` | Нет выдачи; текст неожиданной ошибки не передаётся наружу |

Проверка доступа в этих тестах использует двойник доверенного серверного источника прав. Это проверка границы хранения, не интеграционная приёмка отзыва прав в Odoo. Переходы и ответственность за размещение файла описаны в [архитектуре](architecture.md#хранение-состояния).

Итоговый полный прогон на Python 3.12.10 / pytest 8.4.2: **207 тестов прошли**, из них 48 для этого пакета. После независимой проверки кода исправлены и проверены сценарии исключительного захвата операции, некорректных сохранённых данных и ошибок авторизации. Дополнительно на Python окружения стенда проверены импорт адаптера как подмодуля пакета, создание операции и отказ в чтении сводки во временном SQLite-файле; к базе Odoo проверка не обращалась.
