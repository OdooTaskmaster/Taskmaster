## Правила риска

В [`application/deadline_risk.py`](../application/deadline_risk.py) функция `evaluate_deadline_risk` принимает `DeadlineTaskSnapshot`, момент проверки и часовой пояс проекта. Снимок содержит признаки архивирования и закрытия и нормализованный срок. Для точного срока нужен `datetime` с часовым поясом, для срока без времени — `date`. Если поле невозможно прочитать, снимок отличает это от подтверждённого отсутствия срока. Сырые значения Odoo правило не принимает.

Функция возвращает `DeadlineRiskResult` с одним из трёх исходов: сработало, не сработало, не оценено. Только при срабатывании заполняется `overdue_days`: `0` означает «менее 1 дня», остальные значения считаются по локальным календарным датам. История активности в расчёт не входит.

В том же модуле `evaluate_stalled_deadline_risk` (`RR-02`) использует тот же снимок и расчёт срока, дополняя их временем последнего подтверждённого перехода и признаком полноты истории. При полной истории без переходов отсчёт идёт от создания. `StalledDeadlineRiskResult` содержит дни до срока и дни без движения только при срабатывании.

В [`application/assignee_risk.py`](../application/assignee_risk.py) `evaluate_assignee_risk` (`RR-03`) получает признаки открытости и известные назначения. `None` означает, что назначение не подтверждено и пустоту списка установить нельзя. Пустая последовательность означает подтверждённое отсутствие исполнителей. `AssigneeRiskResult` содержит исход без расчёта дней.

В [`application/inactivity_risk.py`](../application/inactivity_risk.py) `evaluate_inactivity_risk` (`RR-04`) сравнивает последнее подтверждённое событие с датой проверки. Для переходов, человеческих комментариев и регистрации трудозатрат вызывающий код передаёт по одному `ActivitySource`: последнее наблюдаемое событие и признак покрытия истории. Источник трудозатрат пропускается только при подтверждённой неприменимости. При полной истории без событий используется дата создания. `InactivityRiskResult` сообщает число календарных дней без активности только при срабатывании.

Правила используют общий `RiskStatus` и одинаково определяют открытость через `task_is_open` из [`application/risk_status.py`](../application/risk_status.py). Их вызывает прикладная сборка сводки; автоматический вызов из Odoo не подключён. Сценарии агента, запись данных Odoo, REST и обработка очереди не реализованы.

## Сводка рисков

[`build_project_risk_summary`](../application/risk_summary.py) получает функцию чтения, момент проверки и часовой пояс. Читающая сторона передаёт нормализованные снимки задач уже проверенного выбранного проекта в пределах текущих прав получателя. Недоступный проект или сбой чтения она передаёт как `SummaryReadError`, а не как пустой набор. Сам сборщик не обращается в Odoo и не проверяет права повторно.

Сборщик возвращает все строки без лимита. Каждая подтверждённо открытая задача занимает не более одной строки: первое основание определяет группу, остальные подтверждённые основания остаются в той же строке. Ссылка на карточку относительная. Срок и отклонение отсутствуют, если срок пуст или недоступен; признак `deadline_known` различает эти случаи. Булев признак просрочки отличает срок «сегодня» от просрочки «менее 1 дня» при одинаковой величине `0`.

`ProjectRiskSummary` хранит статус, строки и списки проверенных и непроверенных правил. При неполной истории остаются только подтверждённые сигналы, при сбое в середине чтения сохраняются уже собранные строки, но полнота по проекту не подтверждается ни для одного правила. В результате нет текста ошибки источника. Подключение чтения Odoo к сборщику, интерфейс, сохранение и доставка сводки не реализованы.

## Чтение задач Odoo

[`read_project_tasks`](../adapters/odoo_task_reader.py) принимает установленное сервером окружение получателя, выбранный проект, нужные поля и необязательный список карточек. Окружение с повышенными правами отклоняется. При каждом вызове адаптер ищет выбранный проект от имени получателя. Для обычного пользователя требуется запись в «Участниках команды» (`allowed_internal_user_ids`), даже если проект доступен ему в интерфейсе Odoo. Для руководителя пилота (`project.group_project_manager`, администратор Project) членство не требуется. Внутри проекта отдельного фильтра по командам нет.

Для обеих ролей сохраняются штатные ограничения Odoo на компании, записи и поля. Адаптер читает только карточки выбранного проекта и возвращает только запрошенные разрешённые поля из закрытого списка. Скрытые и отсутствующие проекты или карточки не дают строк. Подсчёт допустим только по возвращённой выборке. Подключения к сводке или агенту пока нет.

## Контракты чтения задачи

[`application/task_read_tools.py`](../application/task_read_tools.py) задаёт типы
карточки, описания и наблюдаемой истории и узкие методы, привязанные к
переданному сервером `ScopedTaskSource`. Описание переводится в простой текст
и ограничивается 4000 символами. Парсер обрабатывает не более 262144 входных
символов HTML; достижение этого ограничения тоже выставляет `truncated=True`.
Заголовки, таблицы, списки и блочные элементы разделяются переводом строки,
пробелы (включая неразрывные) нормализуются, пустые строки удаляются.
Период истории — не более 90 включительных
дат календаря проекта. Полнота истории передаётся источником явно.

[`OdooTaskSource`](../adapters/odoo_task_tools.py) привязывается сервером к
окружению получателя, выбранным проекту и задаче и часовому поясу проекта.
Каждый вызов заново использует ту же проверку области и прав, что
`read_project_tasks`; проект и задача читаются без повышения прав. Карточка содержит только разрешённые поля;
непрочитанный срок отличается от подтверждённо пустого. `datetime` без зоны
интерпретируется как UTC, а значение `date` и ISO-строка без времени сохраняют
точность календарной даты, без выдуманного времени суток. Идентификаторы
исполнителей дополнительно фильтруются по видимым `res.users`; имя включается
только при доступности поля `name`. Признак
`assignees_complete` остаётся ложным, а пустое назначение не считается
доказанным, поскольку выборка могла быть ограничена.
Недоступная и отсутствующая задача дают одинаковый ответ `unavailable`.
Ссылка карточки и описания строится как `/odoo/project.task/{id}` — прямой
маршрут записи Odoo, не действие `/tasks`, требующее проектного `active_id`.
Права при открытии формы повторно проверяет штатный клиент/сервер Odoo.

История сначала читает `mail.message` выбранной задачи и периода обычным
окружением и проверяет доступность полей `stage_id` / `state` этим же окружением.
После этого повышает права **только** на `mail.tracking.value`: фиксированная
проекция старых/новых значений по уже разрешённым ID сообщений, модели
`project.task` и разрешённым полям из фиксированной пары. Общий журнал,
произвольный домен или поле через инструмент не доступны. Само окружение
получателя, проекты, задачи, сообщения и этапы не повышаются; ACL не расширены.
Пустая разрешённая выборка сообщений не вызывает привилегированного чтения.
`mail_tracking` включён в зависимости манифеста; старую базу нужно обновить
отдельно, установка не восстанавливает прошлые структурированные события.
Нет модели или необходимых доступных полей — `unavailable`, а не успешная
пустая история. Отказ ACL и ошибки чтения (включая `KeyError`) дают `failed`.
Положительные ID обоих этапов проверяются одним запросом к `project.task.type`;
начальное назначение (ID 0), отрицательные ID и недоступные этапы исключаются.
Источником перехода служит идентификатор `mail.message:<id>`, а не
предполагаемая прямая ссылка. Порядок — по исходному UTC-моменту и числовому ID
сообщения. Изменения stage/state одного сообщения одновременны, их порядок
детерминирован по виду изменения. Значения `state` в истории — локализованные
подписи tracking, **не** технические ключи `TaskCard.state`; их нельзя парсить
как ключи. Даты фильтруются по локальным календарным дням
проекта. Поскольку доступный журнал не доказывает полноту, Odoo-адаптер всегда
возвращает `complete=False`, даже если переходов нет. На один вызов читаются
первые 500 сообщений по дате/ID и до 1000 tracking-значений каждого вида по ID
(до 2000 переходов суммарно; плюс одна строка на вид для обнаружения превышения).
Это предел на поле, а не общий лимит истории. Архивные этапы читаются с
`active_test=False`, но с обычными правами получателя; недоступные этапы
по-прежнему исключаются. При превышении любого лимита выставляется
`History.truncated=True`; наблюдаемое подмножество не выдаётся за все переходы.
Неоднозначная/несуществующая местная полночь или переполнение конвертации
дают `failed`, без подстановки даты. `date.min` в начале и `date.max` в конце
диапазона отклоняются как `ValueError` до ORM. Отдельный прикладной
контракт допускает подтверждённую пустую историю, если другой проверенный
источник может доказать полноту. Локализованный HTML chatter не разбирается.

Регистрация инструментов у агента и финальная повторная проверка всех
использованных источников перед выдачей результата пока не подключены.
Читатели видят снимок `REPEATABLE READ`: отзыв членства, зафиксированный
другой транзакцией, блокирует новое чтение в свежей транзакции, но не меняет
уже начатый снимок (очистка ORM-кэша не помогает). Поэтому финальный барьер
AG-08/AG-10 обязан проверять все источники в свежей транзакции; текущие
читатели не являются таким барьером. Эта граница приёмки #33–35 и отсутствие
HTTP/RPC-публикации до регистрации явно согласованы пользователем.
Проверки адаптера выполнялись модульно и на локальном реальном ORM Odoo 20;
ограничения и сценарии приведены в [проверках](testing.md#узкие-инструменты-задачи-ag-03ag-05).

## Комментарии и трудозатраты (AG-06/AG-07)

`TaskReadTools.read_task_comments(start, end, limit=20)` и
`read_task_worklog(start, end)` дополняют тот же серверно привязанный источник
`OdooTaskSource`. Сначала заново проверяются проект, членство, компания и
выбранная задача; затем вспомогательный модуль
[`adapters/odoo_task_activity.py`](../adapters/odoo_task_activity.py) читает
фиксированные поля источников **без `sudo`**. Лимит, даты и порядок периода
проверяются до ORM; период — не более 90 включительных календарных дней.

Комментарии: `mail.message` только с `model=project.task`, выбранным `res_id`
и типом `comment`, `email` или `email_outgoing` — заметки чаттера и переписка по
email (входящие и исходящие) считаются «разговором»; системные уведомления,
tracking, вложения и сведения об авторах не проецируются. Признак «внутренняя
заметка» не выводится отдельно: состав описан только этим доменом, а
`complete=False` не даёт принять выборку за полную историю. Выбираются последние
сообщения (`date desc, id desc`), не более запрошенного числа от 1 до 20;
одна дополнительная **доступная** строка обнаруживает усечение выборки.
`Comments(fragments, complete, truncated)` содержит `Comment(day, text, source,
truncated)`. Каждый текст нормализуется в plain text, до 2000 символов; вход
парсера ограничен 262144 символами, как для описания. Пустой/только-с
вложением фрагмент занимает слот выборки, но не возвращается как пустой
`Comment` (пропускается прикладным слоем). Флаг коллекции `Comments.truncated`
— объединение «есть ещё фрагменты» и «обрезка текста»; признак текста
`Comment.truncated` точен для отдельного фрагмента. Источник — стандартная
ссылка `/mail/message/{id}`, проверяющая права на сообщение при переходе.
Это свидетельство участника, не подтверждённая причина риска и не инструкция
модели. `complete=False` не позволяет принять отбор за всю историю.

Трудозатраты — необязательная интеграция с `hr_timesheet`; зависимости манифеста
не изменены. Проверяются наличие link-полей `task_id`/`project_id`, права на
все необходимые поля и `project.allow_timesheets`. Статусы: `unavailable, None`
для отсутствующего модуля/поля/проектных настроек или конфигурации единиц при
пустой выборке; `failed, None` для битой строки (дата вне периода, неверный
relation-id строки/единицы, нечисловая сумма). Отсутствующая/некорректная компания
при пустой выборке — также `unavailable`. Недоступная конфигурация единиц
на проекте, у которого есть валидные строки, не делает чтение неудачным.
`account.analytic.line` читается только для выбранных проекта/задачи по **дате
выполнения работы `date`**, не `create_date`/`write_date`. Это отличается от
события регистрации для RR-04. Не возвращаются сотрудники, описания или стоимость.

`Worklog(totals, entries, complete, truncated, period_start, period_end)` возвращает
проверенный запрошенный период и содержит основания
`WorklogEntry(day, amount, unit_id, count, sources)` и суммы
`WorklogTotal(unit_id, unit_name, amount)`. `entries` агрегированы по паре
«день, единица»: `amount` — точная сумма хранимых значений за день в этой
единице (а не построчное округление UI), `count` — число видимых строк,
`source(s)` — ссылки `/odoo/account.analytic.line/{id}` этих строк. Так объём
ответа сокращается при повторяющихся днях/единицах; до 1000 ссылок сохраняются.
Если все пары различны, число агрегатов может достигать числа выбранных строк.
Точное `Decimal` из строкового представления числового ORM-значения может
не совпадать с псевдоокруглённым итогом Odoo по строкам (JSON-публикация ещё
не подключена). Единица каждой строки берётся из `product_uom_id`, имя читается
с правами получателя; архивные единицы читаются с `active_test=False`, чтобы
не делали весь трудозатрат недоступным. Разные единицы суммируются **раздельно**,
без неявного перевода в часы. Единица по умолчанию `company.project_time_mode_id`
выбранного проекта (не `timesheet_encode_uom_id`) резолвится **только для пустой
видимой выборки**: при наличии строк конфигурация единиц не нужна. Нулевое
значение при `complete=False` означает только сумму доступной выборки, не
отсутствие всей работы. Отрицательные корректировки учитываются. Приложение
проверяет даты, уникальность источников, число строк в основаниях, соответствие
сумм основаниям и отклоняет дубли пар «день, единица».

Читаются последние 1000 доступных строк (`date desc, id desc`) плюс одна для
обнаружения превышения. При превышении `truncated=True`: агрегированная сумма
только возвращённых (свежих) оснований, не итог всего периода. Ни скрытые
записи, ни их количество не запрашиваются.
`complete=False` всегда: наличие модуля и успешный запрос не доказывают полный
охват. Недоступные поля дают `unavailable`, ошибки чтения — `failed`, без сырого
текста исключений. Эти инструменты также не реализуют HTTP/RPC-регистрацию или
финальный барьер AG-08/AG-10 в свежей транзакции.

## Порт внешней модели

В [`application/model_port.py`](../application/model_port.py) объявлен `ModelPort` с методом `complete`, а также `ModelMessage`, `ModelRequest`, `ModelResponse` и `ModelFailure`. Запрос содержит только сообщения, необязательный формат ответа, лимит токенов и температуру; провайдерских полей в контракте нет. `ModelFailure` хранит категорию `ErrorCategory` и необязательный HTTP-код, поэтому исходный текст ошибки провайдера не попадает в сообщение исключения.

Порт реализует `OpenAICompatibleModelAdapter` из [`adapters/openai_compatible.py`](../adapters/openai_compatible.py): он собирает payload Chat Completions, преобразует ответ в `ModelResponse` и переводит тайм-аут, транспортный сбой, ошибку провайдера и неверный формат в различимые категории. Клиент не сохраняет текст ошибки провайдера; успешный HTTP-ответ с невалидным JSON или не-объектом классифицируется как `invalid_response`. Повторов, резервной модели и готовых графов нет. Вызов адаптера из Odoo пока не подключён.

Для интерфейса `ModelFailure.user_message` и `user_message(error)` возвращают текст по категории без HTTP-кода, исходного сообщения и стека.

Вендор в коде не закреплён: подходит любой OpenAI-совместимый endpoint, включая RouterAI и OpenRouter. [`adapters/settings.py`](../adapters/settings.py) требует `TASKMASTER_MODEL_API_KEY`, `TASKMASTER_MODEL_BASE_URL` и `TASKMASTER_MODEL`; необязателен `TASKMASTER_MODEL_TIMEOUT_SECONDS`. Пустые или неверные значения дают `missing_secret`, `missing_endpoint`, `invalid_endpoint` или `missing_model`. Ключ хранится в `Secret`, который печатается как `***`, и передаётся только в заголовок транспорта. Провайдер пилота ещё не утверждён; RouterAI в `tools/model_eval/` остаётся только транспортом сравнения моделей из AG-01.

## Журнал действий

В [`application/audit.py`](../application/audit.py) `AuditEvent` содержит действие, исход, UUID операции, числовой ID пользователя, длительность, категорию ошибки и HTTP-код; свободные строки, включая имя модели, исключены. Вызывающий код обязан генерировать независимый случайный UUID v4 (например, `uuid4()`), а не выводить его из проектных данных; проверка версии UUID не доказывает его происхождение. Числовые поля проверяются на тип и неотрицательность. `failure_event` берёт из исключения только категорию и код, отбрасывая недопустимый код; `log_event` пишет одну JSON-строку с префиксом `taskmaster.audit` в логгер `odoo.addons.taskmaster`. События связываются по `operation_id`. Вызовы аудита из Odoo пока не подключены; административного экрана и хранения сырых запросов или ответов нет.

Целевые решения (TO-BE) хранятся локально в `.private/архитектура/`. Точки входа в эти материалы перечислены в [AGENTS.md](../AGENTS.md).
