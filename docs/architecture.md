## Правила риска

В [`application/deadline_risk.py`](../application/deadline_risk.py) функция `evaluate_deadline_risk` принимает `DeadlineTaskSnapshot`, момент проверки и часовой пояс проекта. Снимок содержит признаки архивирования и закрытия и нормализованный срок. Для точного срока нужен `datetime` с часовым поясом, для срока без времени — `date`. Если поле невозможно прочитать, снимок отличает это от подтверждённого отсутствия срока. Сырые значения Odoo правило не принимает.

Функция возвращает `DeadlineRiskResult` с одним из трёх исходов: сработало, не сработало, не оценено. Только при срабатывании заполняется `overdue_days`: `0` означает «менее 1 дня», остальные значения считаются по локальным календарным датам. История активности в расчёт не входит.

В том же модуле `evaluate_stalled_deadline_risk` (`RR-02`) использует тот же снимок и расчёт срока, дополняя их временем последнего подтверждённого перехода и признаком полноты истории. При полной истории без переходов отсчёт идёт от создания. `StalledDeadlineRiskResult` содержит дни до срока и дни без движения только при срабатывании.

В [`application/assignee_risk.py`](../application/assignee_risk.py) `evaluate_assignee_risk` (`RR-03`) получает признаки открытости и известные назначения. `None` означает, что назначение не подтверждено и пустоту списка установить нельзя. Пустая последовательность означает подтверждённое отсутствие исполнителей. `AssigneeRiskResult` содержит исход без расчёта дней.

В [`application/inactivity_risk.py`](../application/inactivity_risk.py) `evaluate_inactivity_risk` (`RR-04`) сравнивает последнее подтверждённое событие с датой проверки. Для переходов, человеческих комментариев и регистрации трудозатрат вызывающий код передаёт по одному `ActivitySource`: последнее наблюдаемое событие и признак покрытия истории. Источник трудозатрат пропускается только при подтверждённой неприменимости. При полной истории без событий используется дата создания. `InactivityRiskResult` сообщает число календарных дней без активности только при срабатывании.

Правила используют общий `RiskStatus` и одинаково определяют открытость через `task_is_open` из [`application/risk_status.py`](../application/risk_status.py). Их вызывают модульные тесты; автоматический вызов из Odoo не подключён. Сборка сводки, сценарии агента, запись данных Odoo, REST и обработка очереди не реализованы.

## Чтение задач Odoo

[`read_project_tasks`](../adapters/odoo_task_reader.py) принимает установленное сервером окружение получателя, выбранный проект, нужные поля и необязательный список карточек. Окружение с повышенными правами отклоняется. При каждом вызове адаптер ищет выбранный проект от имени получателя. Для обычного пользователя требуется запись в «Участниках команды» (`allowed_internal_user_ids`), даже если проект доступен ему в интерфейсе Odoo. Для руководителя пилота (`project.group_project_manager`, администратор Project) членство не требуется. Внутри проекта отдельного фильтра по командам нет.

Для обеих ролей сохраняются штатные ограничения Odoo на компании, записи и поля. Адаптер читает только карточки выбранного проекта и возвращает только запрошенные разрешённые поля из закрытого списка. Скрытые и отсутствующие проекты или карточки не дают строк. Подсчёт допустим только по возвращённой выборке. Подключения к сводке или агенту пока нет.

Целевые решения (TO-BE) хранятся локально в `.private/архитектура/`. Точки входа в эти материалы перечислены в [AGENTS.md](../AGENTS.md).
