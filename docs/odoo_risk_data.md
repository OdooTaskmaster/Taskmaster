# Данные Odoo 20.0 для правил риска

`BL-02.01` · `FR-01`, `FR-03`–`FR-07` · `RR-01`–`RR-04`

Справочник описывает данные стандартных модулей Odoo, а не уже реализованный адаптер. Поля и ограничения сверены по официальным источникам Odoo 20.0; фактические модули, правила доступа и полнота истории на пилотной базе проверяются по [протоколу стенда](odoo_risk_data_verification.md). Функциональные пороги соответствуют правилам пилота из `.private/4_functional_requirements.md`.

## Область проверки и карточка задачи

Выбираем задачи `project.task` с `project_id` выбранного проекта и `active = True`, доступные получателю в его компании и команде. Для фоновой проверки используем сервером определённый контекст получателя, а не права технического процесса. Рабочий этап и статус задачи не взаимозаменяемы: Kanban-колонки настраиваются, статус `Done` или `Cancelled` закрывает задачу независимо от колонки.

| Данные | Модель и поле | Что использовать и как трактовать пропуск |
|---|---|---|
| Проект и компания | `project.task.project_id` → `project.project`; `project.task.company_id` → `res.company` | Область отбора и доступ. Не брать задачи из другого проекта, даже если у них те же исполнители или общий этап. Отсутствие видимости не раскрывать как существование записи. |
| Идентификатор и название | `project.task.id`, `project.task.name` | Для строки сводки и ссылки. Сервер формирует ссылку на доступную карточку из модели и ID. Не использовать портал с токеном как ссылку, обходящую права. |
| Архивация и закрытие | `project.task.active` (`Boolean`), `project.task.state` (`Selection`), `project.task.is_closed` (`Boolean`, вычисляемое) | Открыта: `active = True` и `is_closed = False`. В стандартном исходнике закрыты `1_done` и `1_canceled`; `04_waiting_normal` остаётся открытым. Если состояние прочитать или надёжно определить нельзя, не классифицировать задачу как открытую. |
| Рабочий этап | `project.task.stage_id` → `project.task.type` | Сравнивать реальные переходы по ID этапа. Название колонки, её `fold`, личный этап и `date_end` не доказывают завершение или движение. |
| Срок | `project.task.date_deadline` (`Datetime`, отслеживается в chatter) | У поля может не быть значения. Прочитанное `False` означает «срок не задан», ошибка доступа или чтения означает «неизвестно». См. [точность срока](#срок-и-календарные-дни). |
| Исполнители | `project.task.user_ids` (`Many2many` → `res.users`) | Берём список назначений, а не `project.project.user_id`, подписчиков, автора или одного условного ответственного. Пустой результат считается отсутствием исполнителя только при подтверждённо полной выборке назначений; особенности portal/project sharing могут ограничивать видимость. Архивный пользователь в сохранённом назначении сам по себе не делает список пустым. |
| Создание | `project.task.create_date` (`Datetime`, служебное) | Начало отсчёта, **только если** проверено, что нужный интервал наблюдаем и подходящих событий нет. Если создание неизвестно и другого надёжного основания нет, отсчёт не строится. |
| Последнее обновление этапа/статуса | `project.task.date_last_stage_update` (`Datetime`) | Диагностическая подсказка, не доказательство перехода и не история активности. В стандартном `create()` поле заполняется при присвоении этапа, а `write()` обновляет его при наличии `stage_id` или `state` в изменениях. Повторная запись того же значения может обновить отметку; вычисляемая смена статуса из-за зависимости может её не обновить. |
| Последняя запись / назначение | `project.task.write_date`, `project.task.date_assign` (`Datetime`) | Не использовать как движение или активность: эти отметки не идентифицируют разрешённый вид события. |
| Текст для объяснения | `project.task.description` (`Html`) | Источник для отдельного разбора `UC-02`, не вход правил риска. Читать только разрешённый фрагмент; не считать текст инструкции агента или доказанным фактом. |

## Срок и календарные дни

- ORM Odoo хранит значения `Datetime` в UTC и возвращает их без информации о часовом поясе. Интерпретировать полученное от ORM время как UTC, затем переводить в **согласованный часовой пояс проекта**. Не подменять его часовым поясом сервера или текущей UI-сессии. Источник настройки пояса на стенде фиксируется отдельно; часовой пояс календаря компании не считается настройкой проекта без подтверждения.
- В стандартной карточке `date_deadline` является датой со временем. Виджет оставшихся дней и `hide_time` в календаре меняют отображение, но не тип и не точность значения. Для штатного `Datetime` сравнивать точный момент: срок истёк, если момент проверки позже него. Ровно в момент срока просрочки ещё нет.
- Ветка «срок указан только датой»: дата считается действующей до конца локального дня, то есть просрочка начинается с местной полуночи следующего дня. Применять её только когда источник явно передал дату без времени. У стандартного `project.task.date_deadline` нет отдельного признака такой точности. **Не выводить точность из `00:00`, вида карточки или форматированной строки.** Если на стенде нужен ввод только даты, подтвердить его происхождение и способ передачи точности отдельно; до этого проверять эту ветку нормализованной датой в модульном примере.
- Для порогов 2, 3 и 7 дней вычитать **локальные календарные даты**, а не делить прошедшие секунды на 86 400. Просроченный точный срок сегодня показывать как «менее 1 дня», неистёкший сегодня имеет запас 0 дней, для разных дат использовать разность дат. Момент проверки фиксировать один раз на запуск.

## Источники истории

| Событие | Первичные данные | Что не считать этим событием |
|---|---|---|
| Движение | `mail.message` для `model = 'project.task'` и `res_id = task.id`; при наличии `mail_tracking` связанное `mail.tracking.value.mail_message_id`, `field_id.name ∈ {stage_id, state}` и `field_id.model = 'project.task'`. Момент события берётся из `mail.message.date`. `stage_id`: сравнивать старый и новый ID; `state`: учитывать зафиксированную смену значения. Odoo для `Selection` пишет отображаемые значения в поля `old_value_char` и `new_value_char`; не разбирать локализованный текст как технический ключ текущего статуса. | Создание с начальным этапом, запись того же значения, правка дедлайна, назначение, личная Kanban-колонка, комментарий и трудозатраты. |
| Человеческий комментарий | Доступный `mail.message` той же задачи: `date`, `message_type`, `subtype_id`, `is_internal`, `author_id`, при необходимости `author_guest_id`. Штатное «Отправить сообщение» участником обычно даёт `message_type = 'comment'` и `mail.mt_comment`; `mail.mt_note` относится к внутренней заметке. При разборе текста источником является разрешённый `body` (`Html`). | Не считать все сообщения chatter. Исключить `tracking`, `notification`, `user_notification`, `auto_comment` и другие автоматические записи. `message_type = 'comment'` или `author_id` сами по себе не доказывают ручное действие. Для внутренних заметок и интеграций, пишущих от имени человека, зафиксировать на стенде, как подтверждается происхождение; сомнительное событие не считать подтверждённым комментарием. |
| Запись трудозатрат | `account.analytic.line` с подтверждёнными `task_id` и `project_id` при установленном `hr_timesheet`. `create_date` (`Datetime`) отвечает на вопрос «когда внесли запись», `date` (`Date`) — «за какой день записана работа». Для `RR-04` источник по смыслу «зарегистрирована запись» — момент регистрации `create_date`; `date` показывать отдельно, если нужно указать день работы. Для объяснений дополнительно нужны разрешённое `unit_amount` и единица измерения стенда. | Не считать строки аналитики без задачи, запланированные `allocated_hours` или редактирование старой строки по `write_date`. Не считать сумму по закрытым записям и не подразумевать часы без проверки настроек единицы. |

### Доступность и полнота истории

- На проверенной ревизии `mail.tracking.value` и `mail.message.tracking_value_ids` добавляет отдельный модуль `mail_tracking`. Установленный Project сам по себе не гарантирует его наличие. Без него базовый `mail` формирует HTML-текст изменений в `mail.message.body`. Это не стабильный машинный контракт: **не парсить локализованный HTML** для подтверждения смены этапа или статуса.
- Структурированные значения и поле `tracking_value_ids` штатно ограничены `base.group_system`. Наличие их в админском shell не доказывает доступность руководителю проекта. Для правил и агента не поднимать права через `sudo()`, не добавлять обычного пользователя в системные администраторы и не менять ACL в этой задаче. Если нет согласованного, доступного получателю источника переходов, проверка соответствующего правила неполна.
- `tracking_disable`, `mail_notrack`, импорт, удалённая история, включение трекинга после возникновения событий или обрезка выборки могут оставлять пробелы. Наличие модели или одной найденной записи не доказывает покрытия периода. Проверенный недавний переход может опровергнуть застой; для вывода об **отсутствии** недавних переходов нужен подтверждённый охват. То же относится к комментариям и трудозатратам.
- У `hr_timesheet` проверить наличие модуля, поля `project.project.allow_timesheets` и права на записи под ролью получателя. Если на стенде подтверждено, что учёт времени не применялся к проекту **в проверяемом периоде**, источник можно отметить неприменимым. Если он предусмотрен, но отсутствует, выключен без известной истории настройки или недоступен по правам, не трактовать это как пустой журнал.
- Источники проверяются отдельно от доступности карточки. На выходе и в сохранённых результатах ссылки, счётчики, приоритет и формулировки строятся только на разрешённых данных. Недоступность не должна раскрывать наличие скрытой задачи, её сообщения или записи времени.

## Привязка правил к данным

| Правило | Обязательные входы | Правило и неполные данные |
|---|---|---|
| `RR-01` Просрочка | Открытость, срок с известной точностью, момент проверки и часовой пояс. | Срабатывает при истёкшем сроке. Не требует истории и не отменяется недавним движением. Подтверждённое отсутствие срока: нет сигнала. Непрочитанное поле срока или неизвестная открытость: не оценено. |
| `RR-02` Близкий срок без движения | Входы `RR-01`, история переходов либо `create_date` при полной истории без переходов. | Срок ещё не истёк, запас от 0 до 3 дней включительно, последнее движение было не менее 2 календарных дней назад. При подтверждённом отсутствии срока, сроке вне окна или подтверждённом недавнем движении сигнала нет. В окне с неполной историей без такого опровержения: не оценено. Комментарий или трудозатрата не заменяют движение. |
| `RR-03` Нет исполнителя | Открытость и `user_ids` с известной полнотой. | Подтверждённо пустой список даёт сигнал даже без срока. Любое подтверждённое назначение исключает сигнал. Недоступный или потенциально урезанный пустой список: не оценено. |
| `RR-04` Нет активности | Открытость; переходы, комментарии и регистрация применимых трудозатрат; `create_date` при полной истории без активности; локальная дата проверки. | Берём самое позднее подтверждённое событие из этих источников. Сигнал при разнице не менее 7 календарных дней и покрытии нужного периода; более свежая подтверждённая активность исключает сигнал. Неполный охват без такого опровержения: не оценено. Срок и наличие исполнителя не влияют. |

В расчёте различаем три исхода: **сработало**, **проверено, не сработало**, **не оценено**. Не оценённое правило не добавляет риск, но влияет на статус полноты сводки. Можно показывать подтверждённый `RR-01` одновременно с неполной проверкой `RR-04`.

Задача занимает одну строку в группе самого критичного сигнала, остальные основания перечисляются в ней же. Приоритет групп: `RR-01`, `RR-02`, `RR-03`, `RR-04`. Внутри группы выше идут соответственно более долгие просрочки, сроки с меньшим запасом, ближайшие известные сроки (без срока в конце) и более долгие периоды неактивности. При равенстве используется порядок по ID задачи. Поля сводки строятся только по доступным данным; для отсутствующего срока число дней не вычисляется.
