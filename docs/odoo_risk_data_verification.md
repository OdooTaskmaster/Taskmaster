# Проверка данных риска на стенде Odoo

`BL-02.01` · [справочник полей и правил](odoo_risk_data.md) · [пилотный стенд](development.md#пилотный-стенд)

Матрица ниже содержит **ожидаемые**, а не фактические результаты. Для приёмки нужны обезличенные наблюдения с пилотной базы. Это проверка источников и прав; плагин, агент и автоматический расчёт четырёх правил для неё не нужны.

## Что подготовить

1. Odoo 20.0 и Python 3.12; согласованный тестовый проект, часовой пояс, руководитель и исполнитель. Для проверки политики плагина подготовить задачи в двух проектах: с членством исполнителя и без него. Логин с префиксом команды сам по себе не предоставляет и не ограничивает доступ.
2. Несколько контрольных карточек с разным статусом, сроком и назначением. На тестовой задаче вручную сменить рабочий этап, поменять статус, изменить только дедлайн и отдельно отправить сообщение в chatter. Если трудозатраты включены, внести строку за предыдущий день и сравнить дату работы с датой регистрации.
3. Зафиксировать commit Odoo из каталога его исходников (`git rev-parse HEAD`) и версии (`.\.venv312\Scripts\python.exe --version` и `.\.venv312\Scripts\python.exe odoo-bin --version`). Отметить, включены ли Timesheets и `mail_tracking`, какие права действуют, как настроен часовой пояс, какие события реально наблюдаемы. Не нужно ждать полный демопроект из 20 задач.

## Диагностика в Odoo Shell

Запустить из корня исходников Odoo на согласованной тестовой базе. Заменить `aic_pilot` фактическим именем:

```powershell
.\.venv312\Scripts\python.exe odoo-bin shell -c odoo.conf -d aic_pilot --shell-interface python
```

Сначала сверить наличие модулей, моделей и типы полей. Блоки Python вводятся в Odoo shell. Они читают данные; `commit`, создание записей и изменение прав не нужны.

```python
print(env.cr.dbname)
print(env['ir.module.module'].search_read(
    [('name', 'in', ['project', 'mail', 'mail_tracking', 'hr_timesheet'])],
    ['name', 'state'],
))
fields_by_model = {
    'project.task': [
        'project_id', 'company_id', 'name', 'active', 'state', 'is_closed',
        'stage_id', 'date_deadline', 'user_ids', 'create_date',
        'date_last_stage_update', 'write_date', 'date_assign', 'description',
    ],
    'project.project': ['allow_timesheets'],
    'mail.message': ['model', 'res_id', 'date', 'message_type', 'subtype_id', 'is_internal', 'author_id', 'author_guest_id', 'tracking_value_ids'],
    'mail.tracking.value': ['field_id', 'mail_message_id', 'old_value_integer', 'new_value_integer', 'old_value_char', 'new_value_char'],
    'account.analytic.line': ['task_id', 'project_id', 'date', 'create_date', 'unit_amount'],
}
for model, fields in fields_by_model.items():
    print(model, env[model].fields_get(fields, ['type', 'relation', 'selection']) if model in env.registry.models else 'not installed')

```

Затем явно задать тестовые ID проекта и карточки. ID можно взять с карточки в режиме разработчика. Указать login проверяемого аккаунта. Админский shell используется для поиска аккаунта; саму задачу и источники проверяем через `with_user(user).sudo(False)`, а не под администратором базы. Перед проверкой сравнить активную компанию в UI и в shell: пример использует основную компанию пользователя и контекст его часового пояса только для чтения через ORM, не для расчёта правил.

```python
from odoo.exceptions import AccessError

project_id = 0  # Подставить ID тестового проекта.
task_id = 0  # Подставить ID тестовой задачи.
user = env['res.users'].search([('login', '=', 'aic-pilot-lead@example.test')], limit=1)
assert project_id > 0 and task_id > 0 and user, 'Set the test project, task, and user before continuing'
ctx = {'allowed_company_ids': user.company_id.ids, 'tz': user.tz or 'UTC'}
task_model = env['project.task'].with_user(user).sudo(False).with_context(ctx, active_test=False)
task = task_model.search([('id', '=', task_id), ('project_id', '=', project_id)])
if task:
    print(task.read(['active', 'state', 'is_closed', 'stage_id', 'date_deadline', 'user_ids', 'create_date', 'date_last_stage_update', 'write_date']))
else:
    print('No readable task in this project')

```

Только если карточка прочитана, сверить метаданные источников под той же ролью. Пустой результат здесь диагностический: он не подтверждает полноту периода. `limit=20` ограничивает вывод для диагностики, не определяет окно или алгоритм продуктовой проверки.

```python
def inspect_source(model, domain, fields, order):
    if model not in env.registry.models:
        print(model, 'not installed')
        return
    records = env[model].with_user(user).sudo(False).with_context(ctx)
    if set(fields) - set(records.fields_get(fields, ['type'])):
        print(model, 'field missing or not readable')
        return
    try:
        print(model, records.search_read(domain, fields, limit=20, order=order))
    except AccessError:
        print(model, 'access denied')

if task:
    message_domain = [('model', '=', 'project.task'), ('res_id', '=', task.id)]
    inspect_source('mail.message', message_domain, ['date', 'message_type', 'subtype_id', 'is_internal', 'author_id'], 'date desc, id desc')
    inspect_source('mail.tracking.value', [('mail_message_id.model', '=', 'project.task'), ('mail_message_id.res_id', '=', task.id), ('field_id.name', 'in', ['stage_id', 'state'])], ['field_id', 'mail_message_id', 'old_value_integer', 'new_value_integer', 'old_value_char', 'new_value_char'], 'id desc')
    inspect_source('project.project', [('id', '=', task.project_id.id)], ['allow_timesheets'], 'id')
    inspect_source('account.analytic.line', [('task_id', '=', task.id), ('project_id', '=', task.project_id.id)], ['date', 'create_date', 'unit_amount'], 'create_date desc, id desc')

```

Сравнить вывод с карточкой и chatter. При необходимости системный администратор отдельно подтверждает, что контрольная запись существует, не передавая закрытые сведения пользователю. Повторить проверку под исполнителем для доступных и недоступных карточек. Если пользователь не видит задачу, её источники дальше не читать. Прямые команды Odoo shell показывают штатные права Odoo, а не ограничения плагина: проверку членства в проекте выполняет [адаптер чтения](testing.md#проверка-чтения-задач-bl-0102). Не прикладывать к PR вывод с именами пользователей, сырой перепиской, учётными данными или реальными идентификаторами.

## Контрольные примеры

Фиксированное время для сравнения: **25.11.2026, 09:00 `Europe/Moscow`**. Все даты в таблице локальные. Открытые задачи имеют известную область доступа. Если не сказано иначе: исполнитель есть, история применимых источников полная, последняя активность была вчера. Проверяются только перечисленные в строке правила; знак «нет сигнала» не исключает другие правила. Недоступные записи не входят ни в один проверяемый набор.

| ID | Контрольный вход | Что сверить в источнике | Ожидаемый исход |
|---|---|---|---|
| R01-A | Открыта, срок 24.11, этап изменён сегодня | `state`, `date_deadline`, chatter | `RR-01` есть, 1 день; смена этапа не снимает просрочку. |
| R01-B | Открыта, срок 25.11 08:00; отдельная карточка со сроком 25.11 09:00 | UTC в ORM и локальное время | Первая: `RR-01` есть, «менее 1 дня». Вторая: `RR-01` нет в момент срока. |
| R01-C | Передано только 25.11 без времени | Подтверждённая точность источника; пока её нет в Odoo, это модульный пример | `RR-01` нет в 09:00. Значение `Datetime` в 00:00 не является этим случаем. |
| R01-D | Срок истёк, задача `Done`, `Cancelled` или архивирована; отдельно открытая задача в свёрнутой колонке | `state`, `is_closed`, `active`, `stage_id` | Первые три исключены из проверки. Открытая в свёрнутой колонке остаётся в проверке. |
| R01-E | Срок из ORM: 24.11 22:30 UTC (25.11 01:30 по Москве) | Перевод в часовой пояс проекта до вычисления календарной разницы | `RR-01` есть, «менее 1 дня», а не 1 день. |
| R02-A | Срок 28.11, последнее движение 23.11, сегодня только комментарий | `date_deadline`, переход и метаданные комментария | `RR-02` есть: 3 календарных дня запаса, 2 дня без движения. |
| R02-B | Срок 28.11, статус изменён 24.11; отдельно срок 29.11 со старым переходом | `state` в истории и локальная дата срока | `RR-02` нет в обоих случаях. |
| R02-C | Срок 26.11, история недоступна или обрезана, недавнего перехода не подтверждено | Права и охват источника, не `write_date` | `RR-02` не оценено. После подтверждённого перехода 25.11 можно исключить сигнал. |
| R02-D | Открыта с 23.11, срок 27.11, полная история без переходов | `create_date` и доказуемый охват истории | `RR-02` есть, отсчёт от создания. При недоказанном охвате не оценено. |
| R03-A | У открытой задачи нет исполнителя и срока | Прочитанные пустой `user_ids` и `date_deadline` | `RR-03` есть, дни не вычисляются; `RR-01` и `RR-02` нет. |
| R03-B | У открытой задачи один или несколько исполнителей; отдельно назначения не прочитаны | `user_ids` под реальной ролью | В первом случае `RR-03` нет. Во втором `RR-03` не оценено, а не «нет исполнителя». |
| R04-A | Последнее допустимое событие 18.11; отдельно 19.11 | Даты источников, полнота окна | `RR-04` есть при 7 днях, нет при 6. |
| R04-B | Последнее подтверждённое событие до 24.11 было 18.11. Сравнить человеческий комментарий и только системную запись от 24.11 | `message_type`, подтип, происхождение | С комментарием `RR-04` нет; с системной записью `RR-04` есть. |
| R04-C | Другой активности после 18.11 не было; 24.11 внесена запись времени за 18.11 | `create_date` и `date` у связанной строки | `RR-04` нет: запись зарегистрирована недавно; день работы остаётся 18.11. |
| R04-D | Последнее видимое событие 18.11; источник трудозатрат применим, но не виден. Сравнить с проектом, где подтверждена его неприменимость | `allow_timesheets`, право и охват периода | В первом случае `RR-04` не оценено, во втором `RR-04` есть по оставшимся применимым источникам. |
| MIX-A | Открыта, срок 24.11, история недоступна | Срок и статус читаются, источники истории нет | `RR-01` есть, `RR-04` не оценено; сводка неполная. |
| ACCESS-A | Задача чужой команды или проекта недоступна | Результат `search` под исполнителем, не админом | Ни карточка, ни история, ни вклад в итог не выдаются. |

Если на стенде нет задачи подходящего возраста, зафиксировать относительные условия на отдельном обезличенном примере с опорным временем. Для граничных 2/3/7 дней использовать также эту матрицу в модульных тестах. Не изменять аудит PostgreSQL и не перемещать системные часы ради проверки.

## Что приложить к PR

| Артефакт | Что зафиксировать | Статус |
|---|---|---|
| Паспорт проверки | Версия и commit Odoo, Python, установленные модули, роль, компания и часовой пояс проекта. | Заполняется на стенде. |
| Маппинг стенда | Подтверждённые поля, доступ под руководителем и исполнителем; охват истории и применимость трудозатрат. | Технические имена подтверждены публичным исходником; доступность в базе не проверена. |
| Обезличенный протокол | `ID примера → действие → наблюдённые значения или отметка о недоступности → ожидаемый исход → фактический результат проверки / блокер`. | Ожидания приведены выше. |

Приёмка `BL-02.01` не требует согласования новой архитектуры истории. Если источник не установлен или не читается, зафиксировать причину и какие правила остаются неоценёнными. Не выдавать проверку документации за проверку базы.
